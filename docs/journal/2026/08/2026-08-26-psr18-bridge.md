# 2026-08-26 — The adapter that could not reuse the bridge

Issue **#93**, both criteria. Route `frontier-reasoning / extra` (the `label:adr` protected floor,
per the issue's own routing correction); session model Opus 5 — matched. **ADR-0075** added, spec
**03** frozen.

## It started as a refusal

#93 carries a recorded deferral from the M14 plan pass, and the deferral is explicit that it *is*
the decision, not staleness: *"building a second consumer of an unproven pipeline before the first
one has run once is the wrong order."* Revisit condition: **when #120 has published the PSR-7 bridge
once.**

I checked rather than assumed. `bridge-release.yml`: **zero runs**. No `utils-psr7-bridge-v*` tag.
Split repository: does not exist. Packagist: **404**. #120 open, its first criterion explicitly the
owner's one-time work.

So I stopped and put the evidence in front of the maintainer instead of building. They overrode it.
The ADR records the override — a deferral that was itself a recorded decision deserves better than
being quietly bypassed, and the risk it named is unchanged.

## The assumption that was wrong

The obvious design is "the PSR-18 adapter reuses the PSR-7 bridge for its response conversion." It
cannot, and finding out why took reading both types rather than both names:

- `egl/utils-psr7-bridge` converts the **server** vocabulary — `Request`, `Response`: what an
  application *receives and emits*.
- `HttpClient` speaks the **client** one and returns `HttpResponse` — a different, read-only type.

There is no conversion the two packages share. So the new package depends only on the core and the
PSR interfaces, and a consumer who wants an HTTP client does not acquire a server-side conversion
they never asked for. That is a better outcome than the reuse I set out to find.

## The part that needed real design

PSR-18 separates `RequestExceptionInterface` from `NetworkExceptionInterface` because **only the
second is worth retrying**. The core raises one `HttpClientException` for both a refused scheme and
a dead socket.

The lazy fix is matching the exception message. That breaks silently the day someone rewords a
string — and it breaks in the worst direction, turning a permanent refusal into an infinite retry.

So the classification is **structural**: every request-shaped check runs *before* the send — missing
host, unsupported scheme, and the core's own header guard through `contextOptionsFor()`, which is
public and pure so calling it sends nothing. Anything thrown after that point is the network's, by
construction rather than by inspection.

The scheme list had to be duplicated (the core's is `private`), which this repository already has a
precedent and a remedy for: `QueryBuilder::LIKE_ESCAPE` duplicates `Sanitizer::LIKE_ESCAPE` and a
test keeps them in step. Mine asks the **real core** — that it accepts `http`/`https` and genuinely
refuses `ftp` *before the transport is touched*.

## What the vendors taught me

I wrote a test proving the header-smuggling branch classified correctly. It **errored** on both
vendors: nyholm — *"Header values must be RFC 7230 compatible strings"*; guzzle — *"is not valid
header value"*. Neither will **construct** a request carrying a CRLF header value.

So that branch is unreachable through a conformant implementation. Two honest options: delete it as
dead code, or keep it and say why. It stays — PSR-18 hands the client *a* `RequestInterface` and
guarantees nothing about who implemented it — and it is now asserted against a deliberately
non-conformant double, with the finding in the docblock so the next reader does not delete it as
dead code.

Three other failures on that first run were mine, not the code's: `HttpResponse::$status`/`$body`
are readonly **properties**, not accessors; `contextOptionsFor()` renders headers as a **list of
lines**, not a CRLF-joined string; and a bridge-originated refusal has **no previous exception**,
because the core never saw the request. Each was a wrong assumption about an API I had read too
quickly.

## One pipeline, not two

#93's second criterion says the publication pipeline *reuses* the machinery. Two copies of an
unexercised pipeline is two things to keep true, so the tag now names its package —
`^(utils-[a-z0-9]+-bridge)-v(\d+)\.(\d+)\.(\d+)$` — and the gate prints the directory back for the
split step. A third bridge needs no new workflow.

`bridge_release_gate.py` **had no self-test**. Changing the code that decides *which package gets
published* without one was not defensible, so it has 15 cases now, and the one that matters proves a
tag cannot be satisfied by the other package's version — the two fixture packages hold deliberately
different versions so it cannot pass by accident. A wrong split cannot be taken back.

## Where this leaves the project

28 contract tests × 2 vendors, no network. 15 boundary tests across both packages, plus a new one
that walks `packages/` and fails if a directory exists that the provider does not cover — because a
hand-written list is exactly what silently omits next week's package.

**The risk the deferral named is unchanged, and now one package larger:** `bridge-release.yml` has
still never run, and publishing either bridge still needs the owner's one-time steps. What bounds
it is that every gate runs before any push, and the gate that chooses the package is now tested.
#120 remains the item that closes it.
