# 2026-08-07 — Two answers where the estate had one

Roadmap item **11.2**. The router that replaces 37 deployed folders, each holding an
`index.php` that differed from its neighbours in one line.

## The requirement is the classification

FR-38 reads like a list of features — method matching, `{param}` extraction, callable handlers
— and the part that actually matters is the smallest clause in it: **404 versus 405 with
`Allow`**.

RFC 9110 §15.5.6 makes `Allow` mandatory on a 405 response. So a router that answers "no match"
without saying *why* leaves the application unable to comply with a header it is required to
send, and leaves the caller unable to learn that it used the wrong verb against a path that
exists. Two exception types, and the 405 carries the sorted method list plus `allowHeader()` so
the header cannot be recomputed wrongly by whoever catches it.

This is only possible because item 11.1 unsealed `HttpException` yesterday. The two items were
planned independently and the dependency was real — worth noting, because it is the sort of
thing that usually surfaces as an unplanned prerequisite mid-item.

## Three details that are not incidental

**A placeholder is `[^/]+`, never `.+`.** With `.+`, `/orders/{id}` matches
`/orders/42/lines/7` and hands the handler an "id" of `42/lines/7`.

**Percent-decoding happens after the match.** If `%2F` were decoded first, one parameter could
forge a segment boundary and reach a route it was never given. The routing decision is made on
the bytes the client sent; the captured value is decoded afterwards, when it is data rather than
structure.

**Literal route text is `preg_quote`d.** Otherwise `/files/report.txt` matches
`/files/reportXtxt`, and a route table quietly becomes a place where people write regular
expressions by accident.

Each of these is one character's difference from the wrong version, which is why each has a test
whose failure message says what broke rather than "expected 1, got 0".

## The taxonomy was missing the pattern again

Front Controller was not in `design-patterns.md` — exactly what item 10.4 found for Table Data
Gateway. Two for two on Fowler's *Patterns of Enterprise Application Architecture* entries, which
suggests the taxonomy was seeded from the GoF catalogue and the enterprise patterns were never
added. Worth watching on the next adoption rather than treating as coincidence.

The catalogue row and the taxonomy row both landed, and so did
[`endpoint-kernel.md`](../../../patterns/endpoint-kernel.md) — because the pattern's value is the
~20 lines that stop being copied 37 times, and a one-line catalogue entry cannot show that.

## A guard from four items ago fired on me

The full suite went red on `IdentifierTest::testThePatternAppearsExactlyOnceInTheProductionTree`
— item 10.4's assertion that the SQL identifier allowlist lives in exactly one class, done as a
text scan. My placeholder-name pattern contained the same character class.

The tempting fix was to make the scan narrower. I did not, and the reason is worth writing down:
the natural narrowing is to match only the *anchored* form, and an **unanchored** copy of that
allowlist is ADR-0015's original bug — the one case the guard exists for. Narrowing it would
have traded a security check for my convenience, quietly.

So the router's pattern is spelled `[A-Za-z_]\w*`: same set, different text, with the reason at
the constant. One odd-looking spelling in one file, against a guard that keeps working.

## The same trap, and my guard was pointed at the wrong thing

Five planted defects, five caught — but the third one took three attempts, and it is the second
time this session.

I wrapped the campaign in a helper that verified the plant before believing the result, having
been bitten yesterday. The helper checked that the **replacement string was present** after the
`sed`. For the decode defect the replacement was `$value` — which already occurred elsewhere in
the file — so the check passed, the `sed` had matched nothing, and the suite went green while
reporting "plant verified".

The correct check is the mirror image: **the original must be gone.** A guard that confirms what
you added is worthless when what you added is not unique; a guard that confirms what you removed
cannot be fooled that way.

## Lesson

**Verify a plant by absence, not by presence.** Yesterday's lesson was that a plant which never
landed looks exactly like a caught defect. Today's refinement: the check for it has to be that
the original code is gone, because the replacement is often something the file already contains.
And when the edit is fiddly enough to need escaping, use the tool that fails loudly on a
non-match instead of the one that silently does nothing.
